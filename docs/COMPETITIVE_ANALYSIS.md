## 1. 为什么需要这份文档

用户的原始质疑：

> 小红书搜索旅游攻略，点点能总结笔记内容并给出行程安排，生成速度还很快，并且图文并茂。既然如此，本项目的意义在哪？

这个问题必须先澄清一处事实错位，否则整个差异化讨论会跑偏：

**读者以为在跟「小红书搜索」比，实际在跟「点点」比。** 点点已全量嵌入小红书主站的搜索入口（首页侧边栏、分享笔记、划词提问、搜索框），两者在体验上已经合流。所以本文档的核心竞品是**点点**，不是「搜索」这个动作。

而点点是小红书的 **AI 搜索 / RAG 产品**。TripWeaver 当前的调研层（抓小红书笔记 → 清洗提纯入库 → RAG 检索召回）与点点在架构上**高度同构**。

**这就是结论的前提**：技术路线上我们没有差异，且调研层我们永远做不到点点那么好（语料更全、更新更快、不必抓取）。所以价值必须落在调研层**之外**。

## 2. 竞品全景

| 维度 | **小红书点点** | 通用大模型<br>（豆包/DeepSeek 等） | 垂直 OTA AI<br>（携程/飞猪等）⚠️ | 小红书手动搜索<br>（人工读帖） | **TripWeaver** |
|---|---|---|---|---|---|
| 内容源 | 小红书笔记 + 全网 ✅ | 模型知识 + 联网 | 自有库存 + 交易数据 ⚠️ | 小红书笔记 | 小红书笔记 RAG |
| 时效性 | 近实时（活库）✅ | 弱 | 强（价格/库存）⚠️ | 近实时 | **快照（取决于重抓）** |
| 输出形态 | 对话文本 + 摘要 + 链接 ✅ | 纯文本 | 可下单的行程 ⚠️ | 无（人脑整理） | **结构化数据对象** |
| 结构化程度 | 低（时间轴卡片为主）⚠️ | 极低 | 高（但绑定交易）⚠️ | 无 | **高（坐标/时段/费用/类别）** |
| 地图 / 动线 | 攻略模式含地图能力 ⚠️ | 无 | 有 ⚠️ | 无 | 有（可编辑折线 + 天数过滤） |
| 可编辑 | 多轮对话改文案 | 重问 | 有限 ⚠️ | 手写 | **全字段增删改移** |
| 可交付（发群/打印） | 分享卡片 ⚠️ | 复制文本 | 不可 | 手抄 | **长图/PDF/JSON ** |
| 数据归属 | 平台 | 平台 | 平台 | 自己 | **自己/站长服务器** |
| 门槛 | 装 App | 会用 Prompt | 注册下单 | 会读帖 + 会排 | 点链接 + 填 6 个字段 |

图例：✅ 有来源可核验 · ⚠️ 待核验 · 无标注为常识判断

**矩阵读法**：点点在「内容源 + 时效性」上不可战胜；OTA 在「交易闭环」上不可战胜。TripWeaver 只在**结构化 + 可编辑 + 可交付 + 数据归属**这四列领先，且这四列互相关联（都是「把行程当数据，而不是当文本」的推论）。

## 3. 小红书点点专章

### 3.1 它是什么

| 项 | 值 | 来源 |
|---|---|---|
| 定位 | 小红书 AI 生活搜索助手，覆盖旅行攻略/购物决策/穿搭/美食 | ✅ App Store 应用描述 |
| 内容源 | 小红书真实经验 + 全网信息 | ✅ App Store 应用描述 |
| 技术底座 | 小红书自研「珠玑」大模型；2025-02 接入 DeepSeek「深度思考」 | ✅ 百度百科 |
| 上线时间线 | 2024-08 独立 App（iOS）→ 2024-12-26 正式上线 → 2025-02 深度思考 → 2025-12-04 小红书全资收购开发主体 → **2026 初 上线「攻略模式」** → 2026-05-29 PC 端上线 | ✅ 百度百科 |
| 早期定位 | **初期即聚焦「旅游攻略生成」** | ✅ 百度百科 |

**要点：旅行攻略不是点点的边缘场景，是它的起点和主战场。**

### 3.2 攻略模式（对我们威胁最大的一环）

App Store 版本更新说明原文：

> 全新上线攻略模式，基于小红书海量真人经验，生成专属你的深度攻略，帮你全面搞定旅行攻略、生活兴趣、购物决策、美食探店、笔记总结、知识梳理……

百度百科补充（⚠️ 待实测核验）：

> 2026 年初，点点 App 上线「攻略模式」，能够结合实时信息与地图能力，为用户生成具备时效性和可执行性的深度旅行及生活攻略。

**如果「结合地图能力 + 时效性 + 可执行」这条属实，我们在 F2 地图 上的优势已被官方追平。**

### 3.3 已知弱点（有第三方实测来源）

来源：[人人都是产品经理 —— 「点点」浮出水面，小红书 AI 搜索有了新进展](https://www.woshipm.com/it/6161851.html)

| 弱点 | 原文依据 |
|---|---|
| **幻觉 / 信息过时** | 用户反馈「点点的不足在于有幻觉或信息过时，推荐的店铺无法在大众点评搜索到」 |
| **复杂问题理解偏差** | 「对一些复杂问题的理解还存在偏差，没有准确推荐小红书上的 AIGC 博主」 |
| **无法融合评论** | 「还不能看到点点将更具参考价值的笔记评论内容融合到评价结果中」 |
| **答案来源单一** | 点击「来源」显示的基本都是小红书视频 |
| **消费决策细节有疏漏** | 「能够给出一些方向性的建议，在具体细节上会有瑕疵和疏漏」 |

**这五条弱点，恰好是 TripWeaver 全部可发挥的空间。**

### 3.4 挤压点分级（点点多久会吃掉我们哪一块）

| 我们的能力 | 被挤压程度 | 判断 |
|---|---|---|
| 调研 / 找 POI / 避坑素材 | 🔴 **已被吃掉** | 点点就是干这个的，且语料比我们全。不要在这里投入 |
| 地图可视化 | 🟡 **正在被吃掉** | 攻略模式已声称含地图能力（待核验），要盯紧 |
| 图文并茂的呈现 | 🔴 **已被吃掉** | 点点有笔记原图，我们只有结构化字段，永远比不过 |
| 编辑行程（改时间/换点/移动） | 🟢 安全 | 对话式改稿改的是文本，改不动数据结构 |
| 预算聚合 / 超支预警 | 🟢 安全 | 点点不做账 |
| 交付（长图发群 / PDF / JSON） | 🟢 安全 | 点点的分享是卡片，我们的长图是为微信群场景定制的 |
| 数据归属 / 自部署 | 🟢 安全 | 平台不会给 |

### 3.5 我们相对点点的 4 个真实差异（按护城河强度排）

1. **输出是数据，不是文本。** 点点给你一段话，你得自己抄进备忘录。我们给带 `坐标 + 时段 + 费用 + 类别` 的对象 —— 因此才能上图、能改、能算钱、能导出。**这是唯一的结构性差异，其余三条都是它的推论。**
2. **可复核。** 预算聚合 vs 超支预警、动线审校、坐标地理编码。点点被实测指出「推荐的店铺大众点评搜不到」，我们把坐标钉死。
3. **可交付。** 给爸妈/非 IT 亲友，一次生成一张能发微信群的长图。点点的分享是卡片，不是为你转发给同行人设计的。
4. **数据归属自己。** 自部署，行程数据、编辑历史、导出都在自己的机器上。

## 4. 差异化定位（一句话）

> **点点的终点是「给你一段答案」，TripWeaver 的起点是「把那段答案变成一份可以改、可以算、可以发给同行人的行程」。**

即：**不做攻略的生产者，做攻略的编译器。** 调研层交给点点这一量级的产品去赢，我们只在「答案 → 可执行行程对象」这一段建立价值。

## 5. 风险清单

| # | 风险 | 说明 | 缓解方向 |
|---|---|---|---|
| 1 | **时效性** | 我们的库是快照，点点的库是活的。店关门、涨价、改营业时间，我们的库不知道 | 重抓机制 + 笔记日期入模 + 时效衰减权重 + 过期标注 |
| 2 | **覆盖度** | 库只覆盖抓过的城市。用户输入没抓过的目的地 → 归零，比「慢」更糟 | 必须有兜底路径（通用模型 / 明确提示「暂无该目的地语料」） |
| 3 | **合规** | 抓取笔记入库灰色；开源仓库分发语料敏感 | 语料不入 git；个人自部署；仅存摘要与链接 |
| 4 | **工程量在数据侧** | 清洗提纯质量决定上限，模型编排只是放大器 | 语料质量要有量化指标（见 09-21-eval-system-and-dataset） |
| 5 | **点点持续迭代** | 官方在做攻略模式，地图/时效两条护城河都可能被补 | 持续追踪；把资源压在「编辑 + 交付 + 归属」这条不可能被平台做的线上 |

## 6. 什么情况下这个项目没有意义

判定线（必须先测再回答，不可靠感觉）：

1. **动线质量打不过人工。** 若模型排出的时间/距离/闭馆/预算自洽度，不超过「自己看 3 篇帖子手动排」，那这就是**一个更慢的点点**。
2. **语料覆盖不了用户的目的地。** 若只有三五个城市能用，产品在其余场景归零。
3. **导出/编辑价值不被使用。** 若用户拿到行程后从不编辑、也不导出分享，那第 1 条差异点不成立，项目退化为「点点的慢速劣化版」。

→ 这三条对应 [09-21-eval-system-and-dataset] 与 [09-20-gen-timing] 两个任务，是当前最高优先级。
