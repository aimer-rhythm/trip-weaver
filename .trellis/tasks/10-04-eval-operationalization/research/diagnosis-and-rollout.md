# 评估体系现状与运行方案

日期：2026-10-04。范围：当前工作区代码及本地报告；未查询远端 CI 执行历史，未运行真实服务评估。

## 结论

现有体系能检查历史行程是否满足确定性规则，但缺少持续执行当前生成链路、可比较的版本基线和失败回流。应沿用现有 harness，优先修正 live 隔离与产物保存，再把评估接入开发与定期运行。

## 代码证据与缺口

### 1. 离线 PASS 的证明范围有限

`eval/run.ts` 的默认路径只读取最终 `Trip` 快照并调用 `runChecks`，不会执行当前研究、检索、排程或模型链路。它能防止检查规则和结构契约回归，不能证明当前模型、prompt、知识库或生成实现没有退化。

当前 `orchestrator.ts` 已采用“调研 → 确定性排程 → 文案”的路径。历史最终行程不能覆盖这条新链路。现有各模块单测仍有价值，但需要统一进入评估工作流。

### 2. live 的数据库隔离已经失效

- `eval/run.ts:44` 强制覆盖 `DATABASE_PATH`，注释声称写独立 SQLite `eval.db`。
- `apps/server/src/env.ts:102` 使用 `DATABASE_URL` 作为当前数据库，`DATABASE_PATH` 仅用于旧库迁移。
- `apps/server/src/db/client.ts` 根据 `env.databaseUrl` 建立 PostgreSQL Pool，导入时执行迁移。
- live 会加载 `apps/server/.env`，却没有强制设置评估专用 `DATABASE_URL`。

因此，直接运行当前 live 可能连接环境中的应用数据库，并执行迁移/写入。本轮没有执行该路径。先修复隔离，再产生新基线。

可复用模式：`scripts/verify-generation-flow.mts` 在导入服务模块前创建专用 PostgreSQL 数据库并设置 `DATABASE_URL`；同类隔离也存在于 `scripts/verify-sql-first.mts`。

### 3. 研究与性能指标已接线，但缺少实际样本

09-21 的变更已订阅 `candidate`、`phase_end`、`usage`、`job_done`。当前 9 份快照全部不含新字段，因此这些指标在实际离线报告中均缺席。

采用率是活动名与候选名的匹配率，不是地点真实性或 RAG 召回率。后续应优先用 POI ID/规范实体匹配，结合来源和检索标签，避免重命名造成误判。高采用率也不能证明候选本身正确。

现有 usage 事件含模型 token 与服务调用计数，harness 只保留 token；可补充采集服务调用次数。调用尝试次数、实际出网次数与计费次数必须区别记录，成本估算需带价格版本。

### 4. 新运行会覆盖基准快照

`eval/run.ts:119` 在检查之前直接写入 `eval/snapshots/<caseId>.json`。失败结果也可能替换旧结果。没有“候选运行 → 比较 → 人工接纳”的基线提升流程。

报告没有完整保存运行代码版本、模型配置、输入版本和知识库版本。快照虽有 model，但报告没有将这些来源信息带入。当前工作区有未提交修改，仅记录 Git SHA 也不足以还原本次代码。

### 5. 没有统一的自动执行与对比入口

`.github/workflows/ci.yml` 执行 typecheck、build、生成流程验证和容器验证，但没有执行 `npm run eval`。`.github` 中未发现 eval 定时任务或报告上传步骤；未发现实现中的 `eval/diff.ts`。

`scripts/benchmark-place-retrieval.mts` 是只读 SQL 检索探针，embedding 回调返回 null，没有标注集上的召回断言，不等于完整 RAG 质量评估。

### 6. 场景意图还没有转化为产品断言

9 个用例都有 note，但接口仅含 id、note、form。慢节奏、亲子、住宿、预算等意图没有各自的预期断言。全部 startDate 为空，缺少固定日期下的营业/闭馆场景；近期用户偏好、行程修改、版本恢复也未纳入该金集。

目前 gate 为 hard=0、结构=0、坐标可信且无跳过。预算偏离、路线来源比例、离群点、研究质量、性能均非 gate。不要把 PASS 解释为这些维度都达标。

## 建议的最小落地顺序

### 第一批：可信执行和可追溯产物

1. 修复 PostgreSQL 隔离：显式评估连接配置、专用库、独立账号/密钥，在服务模块导入前生效；拒绝使用应用库。清理仅针对本次创建且校验过名称的数据库。
2. 隔离库导入固定版本的必要知识库数据。明确 rich/sparse/empty 场景，避免新空库意外只测到降级路径。使用脱敏固定数据，不复制用户行程。
3. 每次运行保存到独立 `eval/runs/<runId>/`，快照、事件摘要、单例状态与总报告都保留；不覆盖现有基线。
4. manifest 记录代码 SHA、dirty 状态及改动摘要 hash、用例/快照 schema 版本、模型参数、prompt hash、知识库版本、评估模式与服务配置摘要（无密钥）。
5. 单例状态区分 PASS、FAIL、ERROR、SKIPPED；缺失指标标记 unavailable。live 核心采集缺失须显式失败或降为不完整运行，不能当成 0。
6. 新增报告比较：按 caseId 和兼容版本比较成功率、hard/soft、坐标/路线覆盖、候选采用率、阶段耗时、token 和服务调用。不可比时给出原因。
7. CI 接入现有离线评估和检查器单测，成功/失败均保存报告。提供人工触发 live 的入口和 smoke/full 分组。

验收：能追溯两次独立运行；候选运行失败时基线不变；单例失败仍产生可定位报告；故意注入一条硬违规后 gate 返回非零；可证明业务数据库未被访问。

### 第二批：真正评估当前产品能力

以现有 9 例为起点，先建立 smoke 三例（上海常规、北京远郊、重庆地形），再按问题扩展 full，避免仅增加城市数。

- **确定性回归**：保存候选池、地点事实和受控路线响应，送入当前排程实现重算。独立断言不重复 POI、住宿锚点、远郊独占日、开放日期和节奏上限；避免只让生产 solver 的同一检查函数证明自身正确。
- **Live 生成**：固定输入和数据条件，执行当前研究、检索、排程、文案链路。新快照必须包含候选、阶段耗时与 usage。
- **检索质量**：另建“查询 → 相关实体”标注集，测 Recall@k、实体正确性、证据覆盖；用未参与调优的保留集检查泛化。旧金集 POI 被用作知识库种子不使其失去回归价值，但不能单靠它宣称泛化良好。
- **用户约束**：亲子/慢节奏/明确偏好与排除项转成可检验条件；相同输入只改变一个偏好时，输出应有可解释变化。
- **修改行程**：复用现有详情对话和版本回归脚本，覆盖再加一天、添加地点、换交通、恢复版本；作为独立场景族，不强塞入 GenerateForm 用例。
- **人工体验**：定期盲看少量行程，标注绕路、同质化、简介无用等具体原因。积累标注后再考虑模型评分，自动 judge 分数先做辅助观测。

门槛：结构与硬约束维持零新增违规；历史 54 soft 先逐例归因，再设不退化/分级目标。新指标先建立基线，不凭空制定采用率或耗时阈值。少量 smoke 结果逐例呈现，积累足够同配置重复样本后再讨论 P95 和稳定性。

### 第三批：固定节奏和失败回流

| 触发 | 执行 | 输出与处理 |
| --- | --- | --- |
| 每个 PR | 离线检查 + 受控排程回归 + 相关模块单测 | gate 与报告；硬违规阻断合并 |
| 修改模型/prompt/检索/排程 | live smoke，必要时多次同条件重复 | 与固定基线逐例比较，区别波动与持续退化 |
| 每周或发布前 | full 场景集 + 小样本人工抽检 | 本周退化、新问题、成功率与成本变化 |
| 真实失败反馈 | 脱敏输入 + 失败证据 + 人工确认预期 | 加入对应场景集，修复后保留为回归样例 |

给 live 设置独立的每日预算、调用/时长上限和互斥锁。凭据缺失、外部服务失败和产品质量失败应分开统计，不能删除失败样本来提高成功率。真实服务定时任务在完成隔离和运行授权后启用。

开发者负责修复和技术报告，产品负责人负责抽检及基线接纳。同一人可以兼任，但每个失败必须有归因与后续处理。自动 CI 门槛不替代项目要求的用户验收。

## 完整运行的一次示例

修改“亲子慢节奏排程” → 受控回归验证活动上限与住宿约束 → live smoke 在固定数据上生成 → 报告展示哪些用例变好/变差、调用与耗时如何变化 → 抽检并确认基线 → 将发现的反例补入回归集。

完成这一轮且下一次改动自动重跑、发现退化时有人处理，才证明评估已经成为开发流程的一部分。
