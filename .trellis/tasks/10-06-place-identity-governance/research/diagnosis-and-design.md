## 已确认问题

### 1. 上游别名治理只覆盖少数城市

`xhs-travel-pipeline/app/clean/alias.py` 的 `_ALIAS_MAP` 仅有杭州、北京、成都；济南无配置。上游 `canonical_place` 用 `(city, normalized_name)` 唯一约束。`normalize_name` 清理空白、括号和繁简，但不识别语义同义。

上游同时存在且 active：

| 地点 | 上游 ID |
| --- | --- |
| 大明湖 | 5348 |
| 大明湖景区 | 5953 |
| 大明湖公园 | 5968 |
| 老商埠 | 5371 |
| 经三路老商埠 | 5380 |
| 老商埠经三路 | 5962 |

这些样本的 `amap_poi_id` 均为空；不能指望依赖同高德 ID 的旧合并脚本发现它们。

### 2. 下游事实匹配、检索、候选入池的身份规则不一致

- `lib/placeKey.ts` 会将「大明湖景区」去后缀为「大明湖」。
- `generation/placeRetrieval.ts` 的 SQL 使用原始关键词、名称前缀、已登记 aliases/memberNames。只有 SQL 召回后的行才进入 `rankPlaces` 的名称归一分组。
- 当前下游仅有「大明湖」，其 aliases 为空、memberNames 只有自身；上游的「大明湖景区 / 大明湖公园」不在本次下游导出中。
- 实测关键词检索：搜索「大明湖」返回大明湖及两个相关地点；搜索「大明湖景区」返回空。此结论限定 `vector:'off'`，不能外推为启用向量时必然无结果。
- 老商埠与经三路老商埠在下游均独立存在，aliases 为空、memberNames 只有自身，单次 `rankPlaces` 也保留两条。
- `researchTools.ts:326` 只在当前 knownPlaces 中按原名或明确别名匹配；`:344` 按 `p.name === name` 入池判重；`:354` 创建新的 `uid()`，没有在 ResearchPoi 上保留知识库实体 ID。
- `ResearchPoiSchema` 只有候选实例 ID，无稳定 canonicalPlaceId。后续排程使用候选 ID、名称和对象，无法从已持久化身份保证跨检索批次、跨来源、跨日期的同实体去重。

因此，事实查询能取到同一个地点的信息，不等于检索能召回同一个主实体，也不等于候选池只加入一次。

### 3. 两个商埠条目存在严重地理冲突

| 地点 | 当前地址 | 当前坐标（经度、纬度） | 下游类别 |
| --- | --- | --- | --- |
| 老商埠 | 市中区大观园街道经四路333号 | 116.992757, 36.662082 | 文化 |
| 经三路老商埠 | 济阳区济阳街道经三路 | 117.205681, 36.974469 | 美食 |

当前坐标球面直线距离约 39.6 km。经三路老商埠被匹配到另一行政区的同名道路，属于需要核实的地理异常；须用原始提及与可信地点资料确认正确主体和坐标，不可直接把错误坐标合入主实体，也不可仅因距离远就认定原始提及一定属于两个地点。

上游两条 `place_type` 都是 attraction。`scripts/export_to_tripweaver.py:221` 优先以主题决定 category，再退回 place_type，因此周边美食主题能够把景点转成餐饮候选。需要让实体大类由主体类型决定，主题仅影响兴趣排序。

### 4. 问题不止反馈样本

下游济南还同时存在「五龙潭 / 五龙潭公园」「趵突泉 / 趵突泉公园」同文本归一键组。前一组也存在美食/自然类别冲突。它们是待核实重复候选，不能仅凭文本键自动认定完全等价。

### 5. 导出身份随名字变化

`app/clean/place_export.py:12` 用 `sha256(city + name)[:32]` 生成导出 ID。`identity` 和 `canonicalRedirectTo` 已支持显式主实体与旧 ID 重定向，但仍依赖有限的名称名单。若改了主名而未携带完整历史身份，导出会产生新 ID。

`reconcileImportedPlaces` 可保留照片、来源及历史 ID，是可复用的迁移基础；需要进一步检查重定向链、全库冲突、不同来源的绑定和引用兼容。

## 设计目标

已确认实体在新增提及、改名、重导入、跨来源检索时保持唯一持久身份。未知或有歧义的名称进入明确的解析流程；错误合并可追踪和拆分。完整保证针对已确认身份，不以任意新名称的自动判定 100% 正确为承诺。

## 推荐方案：上游身份注册表 + 下游统一消费

### A. 分开实体身份、展示名称和行程粒度

- `entityId`：持久身份，可保留已有可信主记录 ID；以后改名不重新计算 ID。
- `canonicalName`：可变的展示名。
- `aliases`：同一主体的已核实名称，携带城市/区县上下文、来源、状态、规则版本。
- `externalRefs`：供应商、外部 POI ID、匹配证据和可信度；外部 ID 不是内部主键，也不是单独判等的充分条件。
- `same_as`：两个记录确定同一实体，可合并并保留旧 ID 映射。
- `part_of`：独立子地点属于某景区，保留其预约、营业、坐标等事实。
- `nearby` / `visited_with`：相邻或常同游，不参与身份合并。
- `planningGroupId`：只有明确的行程粒度策略需要时使用；与 entityId 分开，避免把行程去重需求误写成现实地点等同关系。

大明湖/大明湖景区/大明湖公园应作为同义候选核实。超然楼是景区子地点示例，不能因为名称含大明湖就当作别名。商埠几个名称须回看原始提及：若都指同一旅游街区则并为别名；若指历史片区与具体路段则记录包含关系，并在行程层避免重复安排完整游览。

### B. 同一个解析器覆盖存量和增量

处理链：原始提及 → 保守文本清洗 → 同城候选召回 → 证据判定 → 复用实体或登记新实体/待审提及。

- 原始名称和原始上下文保留，不因去括号丢失分店、分馆等信息。
- 已核实 alias / 历史 ID 精确命中优先。
- 后缀规则、词序变化、模糊检索、语义向量、空间关系只负责发现候选。
- 判定综合原文主体、行政区、地址、可信坐标、主体类别、外部地点记录和明确的否定关系。
- 地理距离是证据之一；对缺失坐标、误编码和面积大的景区分别处理，不能使用单个距离阈值作为判等规则。
- LLM 可辅助输出 `same_as / part_of / distinct / uncertain`、来源及解释；自动执行仅限证据充分且无硬冲突的结果，模糊结果进入审阅。
- 同名可能歧义；alias 查询允许返回多个候选，不能建一个无条件覆盖的 city+name 字典后取第一条。
- 归并前校验整个候选组，防止 A≈B、B≈C 的弱匹配传递误吞 C；记录 cannot-link、重定向环及并发冲突。

### C. 全链路传递稳定 ID

- 导出 `entityId` 和旧 ID 映射；导入验证主实体存在、城市/范围一致、无环、无冲突并事务落地。
- 每次检索先解析已知别名，SQL 和向量都折叠到主实体。查询结果不依赖同组成员恰好出现在同一批次。
- `ResearchPoi` 和需要身份的行程活动增加 canonicalPlaceId，保留当前 id 作为候选/活动实例 ID；两者不能互换。
- `add_candidate`、`submit_research`、排程和编辑加点共用实体判等，按 canonicalPlaceId 幂等处理。
- 含歧义或尚无 canonicalPlaceId 的外部地点，先尝试绑定已知实体；保留明确 unresolved 状态及本次解析结果，不靠随机 ID 规避重复检查。
- 入池和最终行程各检查一次同实体重复；明确的重访需求需要独立表达，不能一概删除同地点的不同活动。
- 旧行程按旧 schema 兼容，不静默改写已保存内容。重新生成/编辑时可解析旧 ID；批量历史修复另行明确范围。

### D. 存量修复必须包含事实纠错

1. 审计所有已覆盖城市，生成同义、包含、疑似误定位和类型冲突候选清单；以济南作为首个验收样本。
2. 每个合并计划列出主记录、被归并记录、判断证据、坐标/类别/政策/图片变更及影响引用。
3. 先核实商埠错误地理绑定和景点/餐饮分类。未知值可暂缺，不平均坐标、不任意拿第一条事实覆盖。
4. 事实按字段仲裁：主实体坐标取可靠来源；政策保留适用对象和时间；图片保留来源与主体归属；热度按原始提及去重，不能重复相加。
5. 合并事务写入旧 ID → 主 ID 映射，保留来源与备份，重建导出、检索向量、缓存和派生索引。
6. 保留版本化变更记录与可逆字段差异；重复运行不产生新实体或新重复计数；拆分错误合并也有可执行路径。

### E. 持续验收

- 正例：大明湖名称变体、确认后的商埠同义组，分别检索/不同顺序/跨来源/跨类别入口都解析到同一主实体。
- 负例：大明湖与超然楼、灵隐寺与飞来峰、同名分店、母景区与出入口、不同城市的人民公园。
- 类别污染：游览地点提到美食仍是 attraction；餐厅提到景区仍是 food。
- 地理污染：错误匹配至同名道路不能当作可信主坐标；异常距离进入纠错流程。
- 导入约束：改名 ID 不变；旧 ID 可解析；重新导出导入不复活被归并记录；冲突整批回滚；并发登记不重复创建。
- 全局约束：已核实 alias 的解析具有幂等性，同一 canonicalPlaceId 不因不同名字重复进入常规游览安排。
- 质量观察：独立统计误合并、漏合并、别名未命中、坐标/类型冲突、待审积压和行程重复率。确认过的误合并应作为发布阻断回归；候选阈值须用标注样本验证，不预设凭空准确率。

## 实施拆分建议

1. 稳定身份契约与下游统一判等；使用固定样本证明跨入口一致性。
2. 上游注册/解析流程及主题与主体类别分离；同一机制用于新增和存量。
3. 济南存量修复预览、字段审核、应用与回归，再扩到其余城市。
4. 定期审计、异常报告和审阅结果回流。

仅补济南 alias 可临时缓解样本；仅扩大后缀/子串匹配会增加误合并；完整方案需要身份、事实与消费链路一起闭合。实施过程复用现有导入重定向和身份元数据，避免无必要重建所有基础设施。
