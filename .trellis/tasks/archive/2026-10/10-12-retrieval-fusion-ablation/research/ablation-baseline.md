# 消融矩阵实测：向量通道到底值多少

日期：2026-10-12。方法：`npm run eval:retrieval -- --variants eval/retrieval-variants.json`，只读业务库，`vector` 非 `off` 的变体使用站点 embedding（真实调用）。

## 1. 两个子集

| 子集 | 构造 | 规模 | 字面预期 |
| --- | --- | --- | --- |
| `regression` | `source='goldset'` 主名 + 每个地点首个真别名 | 378 | 命中（回归门） |
| `literalFail` | `research_evidence.content` 不含其地点名、长度 ≥ 25、每地点取最长一条 | **489** | 必然落空 |

`literalFail` 的 489 条比开题时只读探针估的 152 条多：探针统计的是「≥30 字的 evidence **行数**」，脚本按 `DISTINCT ON (place_id)` 取每地点**最长**一条，25–29 字区间补上了其余部分。

## 2. 变体对比结果

| 变体 | 子集 | Recall@1 | Recall@8 | MRR |
| --- | --- | --- | --- | --- |
| `off`（指纹 53a8ab74） | regression | 100.0% | 100.0% | 1.000 |
| `off` | literalFail | **0.0%** | **0.0%** | 0.000 |
| `auto`（指纹 9a43d21b） | regression | 100.0% | 100.0% | 1.000 |
| `auto` | literalFail | 3.5% | 23.1% | 0.087 |
| `force`（指纹 8af50781） | regression | 100.0% | 100.0% | 1.000 |
| `force` | literalFail | 3.5% | 23.3% | 0.088 |

**读法**：

1. `literalFail` 在 `off` 下 0.0% —— 子集构造成功，字面层确实一条都拿不到，这是向量增量的干净对照。
2. 向量把 Recall@8 从 0% 提到 23.1%，**向量通道确实在做实事**，不是摆设。
3. `auto` 与 `force` 差 0.2pt（1 条 query）—— 在字面 0 命中的场景下两者本就等价（`selected.length = 0 < limit`，两个分支都在跑向量），这点差异来自个别 query 的别名恰好出现在 evidence 文本里。
4. `regression` 三个变体全是 100% —— **向量在这一集上零增量**，回归门不动。

## 3. 关键发现：23% 的瓶颈是排序，不是 embedding

`literalFail` 只有 23% 太低，于是做了一次对照实验（临时只读探针，150 条样本，已删除）：

| 排序方式 | Recall@1 | Recall@8 |
| --- | --- | --- |
| A 现行 `rankPlaces` 规则分排序 | 2.7% | 24.0% |
| B 纯向量距离排序（绕过 `rankPlaces`） | **11.3%** | **27.3%** |

**Recall@1 提升 4.2 倍。** 说明向量已经把正确答案召回到候选池里，但 `rankPlaces` 的规则分把它们挤出头部。

探针抓到的典型丢失（均为「距离排序很靠前，规则分落到 8 名外」）：

- 「荔湾区迎春花市，2月14日至17日，地铁陈家祠站或彩虹桥站可达」→ 荔湾路花市：距离第 **1** 位 → 8 名外
- 「免费开放，鸿恩阁傍晚可拍秋日余晖和夜景，公园较大穿舒适鞋」→ 鸿恩寺森林公园：距离第 **2** 位 → 8 名外
- 「日式小食堂氛围松弛环境出片，乌冬、寿司、甜品多次回购推荐」→ 麻布食堂：距离第 3 位 → 8 名外
- 「位置便利，步行可达解放碑、长江索道，设施齐全，性价比高」→ 重庆解放碑平价酒店：距离第 3 位 → 8 名外
- 「高德标注为古镇景区，实际只有大门，无古镇内容，纯属诈骗。」→ 簇锦古镇：距离第 5 位 → 8 名外

### 原因（`apps/server/src/generation/retrievalRanking.ts`）

```ts
score: poiScore(scoreFacts(row), maxima)                        // 热度分，上限 108
  + (exact ? 200 : prefix ? 65 : 0)                             // 字面命中才有
  + (typeof row.distance === 'number' ? (1 - clamp01(row.distance)) * 120 : 0)  // 距离分，上限 120
  + (theme ? 45 : 0) + (categories.includes(row.category) ? 25 : 0) + (coord ? 8 : 0)
  - (!exact && detail ? 100 : 0) - (!exact && parent ? 45 : 0)  // 降权
// 选取循环里还有网格打散：- min(24, cells*8)
```

在「字面 0 命中」的场景下，所有候选都没有 `exact` / `prefix` 分，排序由「热度 + 距离 + 主题/类别 + 网格打散」共同决定：

- **热度分上限 108 ≈ 距离分上限 120** —— 一个高提及量的热门地点，仅靠热度就能压过语义更接近的结果
- `detail` 正则（`[东西南北]门|入口|出口|机位|倒影|转角|停车场`）会误伤名字正常的景点，一条 `-100` 直接归零
- 网格打散最多再 `-24`

即：**把不可比的分数直接相加，且权重固定**。这正是 MimirQ 反复强调的「原始分数跨通道不可比，融合必须显式、确定、可观测」在反向的例子。

## 4. 对原定 P1「通道配额」的修正

原假设：`auto` 模式下向量结果会被字面结果挤掉，需要配额保护。

实测否定了这个假设：

- `regression` 子集字面 100%，向量零增量，配额无意义
- `literalFail` 子集字面 0 命中，`auto` 与 `force` 等价，同样与配额无关
- 而 `auto` 模式**只在字面不满 `limit` 时才跑向量**（`selected.length < limit || vector === 'force'`），所以「字面满额挤掉向量」这个场景在当前代码里不会发生

**P1 的真实问题不是配额，是融合权重。** 向量在排序阶段被热度与规则分淹没。

## 6. P1 落地后的实测

改动：`apps/server/src/generation/placeRetrieval.ts` 在 `selected.length === 0`（字面一无所获）时改用新增的 `rankPlacesByDistance`，其余路径不变；同时新增 `skipped:filled` 与 `vectorSelected` 两个诊断字段（`retrievalRanking.ts` 抽出 `groupPlaces` 供两者共用）。

| 变体 | 子集 | Recall@1 | Recall@8 | MRR |
| --- | --- | --- | --- | --- |
| `off` | regression | 100.0% | 100.0% | 1.000 |
| `off` | literalFail | 0.0% | 0.0% | 0.000 |
| `auto` | regression | 100.0% | 100.0% | 1.000 |
| `auto` | literalFail | **10.2%** | **28.2%** | 0.155 |
| `force` | regression | 100.0% | 100.0% | 1.000 |
| `force` | literalFail | **10.2%** | **28.2%** | 0.155 |

- `literalFail` 的 Recall@1 从 0.0% 提到 **10.2%**，Recall@8 从 0.0% 提到 **28.2%**。改动前是 3.5% / 23.1%（见 §2）。
- 与探针在 150 条抽样上估的 11.3% / 27.3% 量级一致。
- **回归门不动**：`regression` 三个变体仍是 100%。
- `auto` 与 `force` 在 `literalFail` 上完全相同 —— 字面为空时两个分支走同一段代码；差异只出现在字面部分命中的场景（见下表）。

`regression` 的 n 从 378 变为 380：知识库侧新增了两个真别名（并发导入或数据治理），不是抽样漂移 —— 脚本全量执行、无随机性。

### 通道统计

| 变体 | 子集 | 关键词命中 | 向量命中 | 进入结果 | 字面已足够（skipped:filled） |
| --- | --- | --- | --- | --- | --- |
| `off` | regression | 522 | 0 | 0 | 0 |
| `auto` | regression | 522 | 16599 | 2451 | 6 |
| `force` | regression | 522 | 17040 | 2998 | 0 |
| `auto` | literalFail | 0 | 23472 | 3912 | 0 |

读法（不要误读成排序问题）：

- `literalFail` 下 `23472 = 489 × 48`（向量 SQL 的 `LIMIT 48`），`3912 = 489 × 8`（结果 `limit`）。**落差是 limit 截断**，不是排序把向量结果压掉。
- `auto` 在 `regression` 上「字面已足够」只有 6 条 —— 380 条 query 的字面命中总计 522 条（均值 1.37），绝大多数远不满 `limit`，所以向量几乎每轮都外呼。
- `auto` 的「进入结果」在 `regression` 上少于 `force`（2451 vs 2998）是设计结果：auto 把字面命中排在前面，`force` 才做全量重排。
- `vectorSelected` 本身不构成质量指标，只有跨变体比较同一子集时才有信息量。

## 7. 方法学限制（必须与结果一起引用）

- `literalFail` 测的是「**笔记描述 → 找到地点**」，不是「用户搜索意图 → 找到地点」。真实用户不会照抄笔记文本，因此 23% / 27% 既不是上界也不是下界，它的唯一职责是提供一个「字面必失败、语义可能成功」的可复现对照。
- 150 条对照实验只覆盖 `literalFail` 的前 150 条（按 `place_id` 排序），不是全量 489 条；Recall@1 的 2.7% → 11.3% 有抽样误差，但 4 倍量级差距远超噪声。
- embedding 有 10 分钟 / 256 条缓存，两次变体运行会命中缓存；`auto` 变体在 `regression` 子集上多数查询字面已满、不触发调用。
