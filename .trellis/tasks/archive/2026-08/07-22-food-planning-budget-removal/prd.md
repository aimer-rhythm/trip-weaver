# 餐饮编排与预算界面简化

## Goal

把餐饮能力定位为行程编排：每天明确安排午餐与晚餐，并给出顺路的就餐区域、菜系和代表菜建议；实时价格、评价、营业与排队情况交由大众点评/美团等平台确认。同时移除面向用户的预算输入、编辑、页签和费用摘要，避免展示无法可靠维护的价格信息。

## What I Already Know

- 当前规划提示词只要求每天含 1 次正餐，无法保证午餐和晚餐同时存在。
- 当前 9 份 golden 快照中，多数天缺少午餐或晚餐，问题可以稳定复现。
- 预算档位、总预算与活动费用贯穿共享 schema 和旧行程 JSON；直接删除字段会破坏兼容性。
- 前端预算入口包括新建表单、行程信息弹窗、桌面/移动预算页签、编辑器摘要、活动费用编辑、地图费用、打印费用摘要。
- 审校阶段目前仍调用预算工具并按预算档位判断，生成工具允许模型填写活动 cost。

## Requirements

- 每个生成日必须同时包含午餐和晚餐，不能只依赖提示词约束。
- 规划提交前把缺少午餐/晚餐视为完整性问题并要求模型修复。
- 审校结束后再次检查餐次；若模型仍遗漏，系统以确定性兜底补齐后再持久化。
- 审校模型达到单阶段轮次上限时，不得使整次生成失败；保留已完成修订，转入确定性餐次与可行性检查后正常落库。
- 坐标与路线解析后，若某地点与另一天的地点显著更近，系统可尝试交换同类游览块；只有真实通勤明显下降且硬违规不增加时才采纳，否则完整回滚。
- 审校删除、换天或改写活动后，最终落库前必须重算通勤段，不得持久化指向已不存在活动的 stale legs。
- 自动补餐和最终时间修复必须为真实通勤预留间隔，不能让后一活动紧贴前一活动结束时间开始。
- 午餐建议时段为 11:00-14:30，晚餐建议时段为 17:00-21:30；明确带有“午餐/午饭/中餐”或“晚餐/晚饭”语义的餐饮活动也可识别。
- 新餐饮活动强调就餐区域、当地菜系和代表菜，不把具体餐厅当作不可替换的硬依赖。
- 餐饮描述明确提醒用户到大众点评/美团等平台确认实时价格、评价、营业和排队情况。
- 调研得到的餐饮 POI 可作为区域和菜系参考或候选，但不得把评分、价格、营业或排队信息当作稳定事实写入行程。
- 移除新建行程的预算档位和总预算表单项；请求继续发送兼容默认值 `budgetLevel: 舒适`、`totalBudget: 0`。
- 移除行程信息弹窗中的预算字段、编辑器桌面/移动预算页签、预算摘要和打印费用摘要。
- 移除活动费用的新增、编辑和展示；新生成不再要求或允许模型估算 cost。
- 保留共享 schema、持久化 Trip 中的 `budgetLevel`、`totalBudget`、`cost` 以及旧预算纯函数，确保旧数据与现有 API 仍可读取和保存。

## Acceptance Criteria

- [ ] 规划草稿任意一天缺午餐或晚餐时，`submit_plan` 返回具体缺失项且不通过。
- [ ] 最终持久化前每一天都能识别到午餐和晚餐。
- [ ] 兜底餐次不会覆盖已有午餐/晚餐，活动按时间顺序插入。
- [ ] 当餐窗没有可用空档时，兜底会把餐次安排并入跨越该餐窗的既有活动，避免制造时间重叠。
- [ ] 审校阶段超过 12 轮时任务仍以 `job_done` 收敛，并在审校说明中标记降级。
- [ ] 跨天近邻优化用真实路线复验，通勤收益不足或新增 hard 时逐字节回滚。
- [ ] 最终 Trip 的每条 leg 两端均为当天当前相邻活动或有效住宿哨兵，不含已删除活动 ID。
- [ ] 自动补齐餐次与相邻活动之间至少留出确定性移动缓冲，最终时间线不产生贴边通勤 hard。
- [ ] 餐饮提示词不再要求具体餐厅价格或评分，明确外部平台确认边界。
- [ ] 新建页、行程信息弹窗、编辑器、地图和打印视图不再出现预算/费用控件或摘要。
- [ ] 旧行程 JSON 中已有预算与 cost 字段仍通过 schema 并可保存。
- [ ] 新生成请求使用兼容默认预算值，新生成活动不产生新的 cost 估算。
- [ ] 相关单测、`npm run typecheck` 与 `npm run build` 通过。

## Definition of Done

- 生成编排、审校和最终持久化路径均覆盖餐次完整性。
- 确定性餐次识别/补齐逻辑有聚焦单测。
- 预算 UI 与新生成预算决策移除，旧数据契约保持兼容。
- 项目规范记录新的餐饮编排与兼容边界。

## Technical Approach

在 server generation 层新增纯餐次识别与补齐模块，由 `DraftTrip.validate()` 复用识别结果形成提交门槛，并由 orchestrator 在审校后执行最终兜底。兜底根据当天已有活动形成“午餐/晚餐｜就近片区·当地风味”占位建议，使用固定餐窗并按时间排序；随后让现有 geoPipeline 解析与重算通勤。提示词与 reviewer 工具移除预算决策，强化区域/菜系/外部确认边界。

前端只移除预算和费用交互，不改共享持久化 schema。生成请求在客户端填充兼容默认值，确保服务端与旧版本调用契约稳定。

## Decision (ADR-lite)

**Context**: 平台没有大众点评/美团交易与实时数据能力，但餐饮时段仍直接影响路线和日程可行性；同时预算估算缺少可信实时数据。

**Decision**: TripWeaver 负责“何时吃、在哪个片区吃、吃什么类型”，外部本地生活平台负责具体门店、价格、评价、营业、排队与交易。预算字段只作为历史兼容数据保留，不再面向用户或参与新生成决策。

**Consequences**: 行程每天具备完整餐次且产品承诺更可信；旧数据无需迁移。系统仍不提供实时餐厅决策，用户需要跳转外部平台确认。

## Out of Scope

- 接入大众点评、美团的商业 API、团购、排队、预约或支付。
- 删除数据库或共享 schema 中的历史预算字段。
- 为旧行程批量补齐餐次或清除历史费用数据。
- 在本任务中重生成全部 live golden 快照。
