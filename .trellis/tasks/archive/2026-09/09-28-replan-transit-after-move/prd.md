# 移动活动后重新规划并恢复相邻路段时长

## 状态

2026-09-29 用户要求实施移动排序后的自动交通规划，并确认综合推荐：实际步行路线不超过 1 公里时优先步行，其余按实际耗时最短选择。

## 现象及已知原因

上下移动或跨天移动活动后，原先显示的交通时长消失。
当前路段绑定 fromActivityId / toActivityId，展示层只匹配当下相邻活动对；顺序改变后原路段失配而隐藏，尚无自动重新查询路线的流程。不能直接复用旧活动对的时长到新活动对。

## 需求

- 同一天重排、跨天移动后，识别源天与目标天受影响的相邻路段。
- 为新相邻活动对重新查询路线、耗时与距离，并更新显示及持久化数据。
- 未受影响的有效路段继续保留；重算期间显示状态，失败提供重试。
- 缺坐标或无可用路线时明确说明，不能显示错误路段的旧时长。

## 验收草案

- [x] 上移、下移、跨天移动均能获得与新活动对一致的时长。
- [x] 原来未改变的有效路段保留。
- [x] 连续移动时过时响应不会覆盖最新活动顺序。
- [x] 重新打开行程后保留正确路段信息。
- [x] 重算中、失败、缺坐标和不可达状态有反馈。

- 后续交互补充：正常查询中和成功后不显示刷新按钮，仅失败时显示“重试”；点击立即显示转圈图标与“查询中…”，所有方式结束后成功则隐藏、失败则保留重试。查询中禁用重复点击，支持减少动态效果。浏览器验证正常隐藏、失败显示、loading 与成功隐藏。

- 全仓 typecheck、web build 通过。
- editorStore / recommendedRoute / routeQueryQueue 共 9 项测试通过。
- route-options-browser 回归通过：1 公里优先步行、超过阈值选最快方式、源天失败后重试、隐藏目标天自动规划并保存、重开恢复、手动选择、移动端样式。
- 浏览器采用模拟路线 API；本次未进行真实高德上游调用。

## 实施决策

- 复用已完成的分方式查询 API、React Query 缓存和串行队列，无需新端点。
- 上移、下移、跨天移动后仅为新相邻活动对安排任务；源天和目标天均覆盖，即使某天没有显示在页面中。
- 实际步行路线 <=1000m 优先步行，否则最短 durationMin，同耗时以更短距离为准，再按 walk/cycle/transit/drive 稳定排序；不采用启发式结果。
- 任务持有活动对指纹与独立请求 ID。连续移动、坐标修改、切换行程或手动选择使旧任务失效。失败可重试；没有任何可靠方案时不写虚构交通数据。
- 自动选择与手动选择共用 draft、地图和串行自动保存；查询状态是编辑器临时状态，不作为路线结果持久化。
- 加载旧行程不自动覆盖已有路线；住宿锚点的自动重算不在本任务范围。
