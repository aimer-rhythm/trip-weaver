# 详情页对话优化与历史版本：流式回答、关联建议、版本查看与恢复

状态：实现已交付自测，待用户验收 v0.5；用户于 2026-10-02 明确选择“按现有方案开始实现”。保留添加方案 A、右上角历史版本入口、查看与恢复需求。
本轮进入代码实现。设计确认不等于实现验收；实现自测后另行交付用户验收，再按授权提交、归档。

## 1. 目标与已明确需求

让用户在行程详情页边看行程边获得即时回答，并能将查询结果直接用于完善当前行程。

- 回答采用真实流式输出。
- 对话字体改为 16px。
- 思考内容折叠显示。
- 行程生成完毕后出现可点击建议，例如“推荐美食”。
- 建议结合当前行程；查询到的具体美食地点可添加到行程。
- 详情页右上角增加“历史版本”按钮，支持查看和恢复历史版本。

## 3. 交互设计

### 3.1 布局与视觉

沿用现有颜色、圆角、图标与详情页布局，不引入新的视觉主题。

- 对话正文、用户消息、输入框、思考摘要、建议按钮和美食说明为 16px，正文行高 1.6（约 26px）。日期/来源等辅助元数据可 14px。
- AI 消息和结果卡利用可用面板宽度；用户气泡继续右对齐。段落间距 8px，消息间距 16px。
- 输入区固定在面板底部；建议位于最新完整回答下方，最多 3 个，自动换行。
- 375px 窄屏使用单列卡片，无横向滚动；操作触达区域至少 44px。折叠控件支持键盘和 aria-expanded。
- 流式自动跟随仅在用户已接近底部时生效；用户上翻后显示“回到最新”，不强拉滚动。

### 3.3 流式回答与折叠思考

1. 点击发送后立即出现用户消息；等待首段正文时显示处理状态。
2. 思考区域默认收起，标题随状态显示“正在分析行程”“正在查找附近美食”“思考摘要 · 已完成”。用户可展开查看简短步骤与依据摘要。
3. 展示面向用户的处理摘要或供应商提供的可展示摘要，不要求或暴露原始内部推理、提示词、工具 JSON。无摘要时不显示空折叠块；不用假思考填充。
4. 正文随上游增量到达显示；不可把完整回答取回后用定时器逐字播放充当流式。
5. 结构化卡片在校验完整后出现，避免半张卡片可点击；新建议在本轮成功完成后出现。
6. 发送按钮在回答中变为“停止”。输入框允许写下一条草稿，但同会话只执行一轮，避免并发顺序混乱。
7. 停止或断流保留当前屏幕的部分正文，标注“已停止/回答中断”，提供重试；未完成内容不标作成功回答。用户失败输入可以恢复编辑。
8. 有副作用的修改须先校验再执行；修改已成功但连接断开时，通过操作结果恢复，不重复添加、不显示误导性的取消成功。

### 3.4 建议的出现与上下文

- 生成成功并进入详情页后即可出现 3 条起始建议，不额外调用模型，不自动发消息、不自动查询。
- 建议默认：“推荐美食”“看看沿途玩法”“检查行程节奏”。后两项先提供咨询回答；本期完整卡片添加闭环优先美食。
- 有明确选中日期时，建议绑定当天；无明确日期时绑定整趟行程，结果注明对应日期，不能默认为第 1 天却不告知用户。
- 点击建议作为一次用户消息直接发送，消息文案带出范围，例如“推荐第 2 天路线附近的美食”。按钮动作携带可信上下文，不能只靠短标签推断。
- 推荐考虑目的地、当日景点位置和顺序、交通方式、已安排餐饮，以及已知的饮食偏好/忌口。缺少预算不阻塞查询。
- 回答完成后最多给 3 条后续建议；美食场景可为“再推荐几家”“换成清淡口味”“看看晚餐”。避免固定重复和无依据的偏好推断。
- 仅最新一轮建议可操作。切换日期/版本后重建当前建议；历史卡片可以阅读，写操作需重新检查当前版本适用性。
- 无关联会话时显示可恢复的提示，不让建议按钮点击后无反馈；历史/导入行程的会话补建可复用现有入口能力，需实现阶段核实。

### 3.5 美食查询结果

每轮优先展示 3 张卡片，不足 3 个时按真实结果数量显示。

必需：具体店铺/分店名称、地址或可核验位置、推荐理由、关联日期/附近景点、证据来源、稳定候选标识。

可选：菜系、特色菜、人均、营业时间、交通距离/时长。没有证据的字段省略或标注未知；估计值注明“约/估算”，直线距离不能写成步行距离。图片非必需，缺图用现有类别图标。

- 使用已验证地点库、已有 POI 和网页检索适配器；按可用能力降级，不让模型凭记忆伪造“查询到的餐厅”。具体数据源覆盖需实现时验证。
- 只有能解析为具体地点的结果可直接添加。“本地小吃”等泛化菜名只给文字介绍和“查找店铺”。
- 查询无结果、数据源不可用或额度不足，明确展示对应状态，提供换区域/口味或重试；不生成虚构卡片。

### 3.6 添加到行程（已选择方案 A）

用户已选择方案 A：卡片直接显示“加入第 2 天 · 午餐”，旁边有“调整位置”。主按钮点击即执行该明确位置的添加；需要更换日期或活动前后位置时打开轻量选择层，不另设“是否确认”弹窗。

执行规则：

1. 位置明确后才可添加，推荐位置考虑前后景点与用餐时段；不能确定合理位置时必须选择位置。
2. 使用服务端保存的候选数据和 ID，不把卡片正文重新发给模型猜店名。
3. 添加一个餐饮活动到目标位置；复用活动与局部调度规则，补齐/重算受影响交通段和必要时间，不无故重排整趟行程。
4. 若时段冲突、营业信息明确不匹配或已有用餐活动，提示具体原因并让用户调整位置；不暗中替换原活动。
5. 保存成功后显示“已加入第 2 天”，同步行程列表与地图、定位到新增活动；保留对话阅读位置。保存失败不显示成功。
6. 延续现有修订版本链，生成新版本。提供“查看新增活动”和本期新增的右上角“历史版本”入口，通过版本恢复回退到添加前的行程。
7. 按钮执行中禁用、同一请求幂等；同一天同一 POI 重复添加需阻止并定位已有活动，不按同名误合并不同分店。
8. 提交绑定当前保存版本；历史预览只读，可“返回最新版本”或“恢复此版本”后再添加。编辑器有未保存修改时先完成现有保存流程，保存失败则停止添加，避免覆盖草稿。
9. 普通自由文本明确要求修改仍沿用已确认的直接修订方式。“推荐美食”及其查询建议不自动生成或修改行程。

### 3.7 方案 A 的位置与状态细节

推荐位置除日期和餐次外，在卡片操作上方显示活动锚点，例如“景点 A 之后 · 景点 B 之前”。推荐时段仅为建议，最终以保存后的行程时间为准；不能通过按钮文案隐瞒时间冲突。

“调整位置”打开就地选择层（窄屏可用底部面板），默认带入推荐日期与位置：

- 日期：选择当前行程实际存在的天数，并显示日期。
- 位置：选择当天某活动之前/之后，或当天末尾；空白日提供“当天第一个活动”。
- 摘要：显示“第 2 天 · 景点 A 之后”，有冲突时显示具体原因。
- 操作：“添加到这里”执行一次添加；“取消”关闭，候选和原推荐位置保持不变。该选择层本身就是操作入口，不再弹二次确认。

| 卡片状态 | 主操作 | 行为 |
| --- | --- | --- |
| 地点与推荐位置明确 | 加入第 2 天 · 午餐 | 直接提交该位置，旁边可调整 |
| 地点明确但无合理默认位置 | 选择添加位置 | 打开位置选择层，不猜测时段 |
| 推荐餐次已有用餐活动 | 调整位置 | 提示“该时段已安排用餐”，不自动替换；非重叠的加餐仍可选择 |
| 正在提交 | 正在添加… | 禁用重复提交和位置更改 |
| 已成功添加 | 已加入第 2 天 | 展示“查看新增活动”，返回保存结果中的真实日期 |
| 同日已存在该地点 | 行程中已有 | 定位已有活动，不新增版本 |
| 添加失败 | 重试添加 | 保留选择；同一操作标识重试，先检查原操作是否已完成 |
| 查询后行程被修改 | 更新推荐位置 | 重新校验候选与当前日程，不沿用过期活动锚点 |
| 当前查看旧版本 | 前往最新版本 | 先切换版本，再由用户操作添加，不静默跨版本写入 |

成功添加一张卡片后，其他候选不会直接作废：先映射至新版本并重新检查推荐位置。已占用的餐次改为“调整位置”，避免连续点击把数家餐厅塞进同一午餐时段。用户手动删除已添加活动后，刷新卡片状态，以实际行程为准。

### 3.8 完整使用示例

以下店铺与景点名称均为交互占位，不代表真实数据。

1. 用户进入已生成行程，选中第 2 天，点击“推荐美食”。
2. 对话出现“推荐第 2 天路线附近的美食”；折叠状态依次显示分析行程、检索餐厅；回答正文实时出现。
3. 餐厅卡片说明“适合第 2 天午餐，景点 A 之后”，并给出实际检索来源。
4. 用户点击“加入第 2 天 · 午餐”，按钮变为“正在添加…”。
5. 保存成功，行程切到新版本，列表和地图定位餐厅；卡片显示“已加入第 2 天”，对话不重新滚回开头。
6. 其他卡片重新核对位置；后续建议变为“看看晚餐”“再推荐几家”等适用选项。

### 3.9 右上角历史版本入口

- 在详情页右上角工具栏、导出按钮左侧增加“历史版本”按钮，使用历史图标与文字，不藏进导出菜单。窄屏仍保留清楚可见的文字入口，必要时工具栏换行。
- 点击打开右侧历史版本面板；窄屏使用全屏面板，带标题和关闭按钮。面板内独立滚动，不压缩行程内容到不可读。
- 按版本从新到旧显示：版本号、创建时间、已知变更来源/摘要，并分别标注“最新版本”和“正在查看”。没有可靠变更摘要的旧记录仅显示版本号、标题与时间，不编造来源。
- 每条历史记录提供“查看”“恢复”操作；最新版本提供“查看”，不提供恢复自身。仅有一个版本时仍可打开，显示“暂无更早版本”。
- 版本加载中、加载失败/重试、记录已不可用均需可见反馈；列表不能把加载失败误显示成无历史。

```text
详情页右上角                         [历史版本] [导出]

历史版本                                      [关闭]
v5   最新版本 / 正在查看
10-02 18:30 · 添加餐饮活动                    [查看]
v4
10-02 18:10 · 行程修订                [查看] [恢复]
v3
10-02 17:50 · 从 v1 恢复              [查看] [恢复]
```

以上时间和摘要为界面示意。恢复来源仅在服务端有记录时显示。

### 3.10 查看历史版本

- “查看”在当前详情页加载所选版本，地图、日期列表和活动详情与该版本一致，并关闭历史面板以留出阅读空间。
- 页面顶部显示“正在查看历史版本 v3”，提供“返回最新版本”和“恢复此版本”。刷新/直达历史版本 URL 仍保持只读。
- 查看不产生新版本、不改变最新版本、不消耗额度。
- 只读约束覆盖编辑、拖拽、删改、备选添加、美食卡片添加、自动保存及自动路线写回。历史预览保留已有对话阅读，暂停发送新对话；提示“返回最新版本或恢复此版本后继续对话”，避免会话误操作最新行程。
- 导出可用于当前查看的历史内容；不改变导出任务本身的设计。
- 当前最新版本有待保存修改时，先完成现有保存队列再切换；保存失败留在当前页面并提供重试，不丢弃草稿。对话或添加/恢复操作进行中时可打开列表，但切换与恢复需等当前操作结束。

### 3.11 恢复历史版本

恢复语义：将所选历史内容复制成新的最新版本，保留所有已有版本。例如当前 v5，恢复 v2 后产生 v6，v6 内容来自 v2；v2、v3、v4、v5 仍可查看或恢复。

- 在历史列表或预览横幅点击“恢复”，就地显示操作说明：“将 v2 的内容恢复为最新版本，现有版本会保留。”操作为“恢复为最新版本”和“取消”，不依赖浏览器原生确认框。
- 恢复包括行程标题、日期、活动、住宿、交通及已保存的行程内容；使用新的行程 ID、版本号和创建/更新时间。保留原有活动及路线关联的一致性，不触发模型重新生成或重新查询以改变历史内容。
- 恢复不倒退对话消息历史、不回滚用户设置或配额。对话关联和后续问答上下文更新到新版本，显示“已从 v2 恢复为 v6”的系统操作记录；已有推荐卡重新校验适用性和已添加状态。
- 恢复成功后切换新版本，退出只读状态，同步行程列表、地图和版本面板；保留仍存在的当前日期，否则回到总览。
- 恢复不消耗 AI 对话或行程生成次数。执行中禁用重复点击，失败保留当前内容并可重试；重试使用同一操作标识，断线后先查询结果，不能生成重复版本。
- 同时提交当前最新版本标识；若期间其他标签页完成修订，提示“行程已有新版本，请刷新后再恢复”，刷新后由用户重新操作，不静默覆盖变化。
- 无关联会话的导入/旧行程也能独立查看和恢复；不强制建立 AI 会话。
- 历史范围以已保存版本链为准。现有手动编辑是原地自动保存，本期不把每次按键或拖动生成一个历史版本；界面说明“记录生成、修订和恢复产生的版本”。新版本建立后旧版本必须冻结，防止迟到的自动保存篡改历史。未曾保存为版本的更早内容无法补回。

## 4. 技术设计方向（实施前细化契约）

- 采用带鉴权的 POST 流式响应（fetch 读取 SSE），便于随消息提交当前行程和日期；复用已有生成事件机制的约定，不误用仅支持 GET 的原生 EventSource。
- 增加共享事件契约：accepted、progress、answer_delta、recommendations、edit_result、done、error。事件携带 requestId/sequence；终态唯一、按序去重。
- 将面向用户的正文流与结构化决策分离。当前 reply 位于工具参数里，且 runner 仅在 message_end 上报正文，需贯通真正的上游文本增量；不把工具参数/思考增量当作回答。
- 当前 runner 默认关闭 thinking，本期不为折叠区强制打开昂贵推理模式。处理状态来自真实检索/校验步骤。
- 发送上下文含 conversationId、tripId、版本或修订标识、可选 dayId；服务端验证所有权、会话关联和版本新鲜度，不能信任客户端任意 POI/活动内容。
- 候选与建议采用结构化共享 Schema，关联源行程版本、日期、候选来源和校验状态；完成消息持久化卡片和可展示摘要，刷新后可恢复。
- 流式失败/停止的未完成问答不记为成功回合，保持现有失败不消耗对话额度约定；部分文本仅本地保留。本轮成功仍成对落库用户和助手消息。
- 添加操作使用持久化 operationId 与幂等结果，确保新版本、消息关联与结果记录一致；断线后的重试可返回原结果。
- 建议展示免费；建议查询成功按一轮对话计费、不消耗行程生成次数。候选添加建议使用确定性接口，不额外调用 LLM、不扣生成或对话次数；外部检索仍遵守现有来源额度。此为本期拟定口径，确认后更新规范。
- 避免查询建议被误判为 confirm 而触发全量生成。保留已有明确重新生成意图的流程。
- 复用 `GET /api/trips/:id/versions`、`useTripVersions`，补充当前/最新版本、恢复来源等可靠元数据。新增恢复接口，接收历史源版本、预期最新版本和幂等 operationId，服务端校验同一用户、同一版本链。
- 当前 `revisionLineage` 使用目标版本号 + 1；恢复不能把历史源直接当 revisionOf，否则会产生重复版本号。复制源为历史版本，父版本为事务内核验的最新版本，新号沿版本链递增；并发校验、版本分配、插入与操作记录保持原子性。
- 恢复后的会话锚点需纳入现有 `latestConversationTrip`/来源会话反查逻辑，不仅依靠新 generation 记录；没有会话的版本链照常恢复。
- 前后端都约束旧版本写入；最新版本的原地保存须带修订标识做并发校验，创建下一版本与待完成自动保存协调，历史预览禁用自动路线写回。现有总行程条数限制仍适用，达到上限时返回明确失败，不静默删历史腾空间。

## 5. 验收标准

以下勾选保留给用户验收，不以 AI 测试结果代替。已执行的自测及限制见 [实施记录](research/implementation.md)。

- [ ] 延迟测试中，上游首段到达后立即显示，后续段落逐步出现，直到终态；不是整段到齐后动画。
- [ ] 用户/AI/输入/思考和建议主要文字 computed font-size 为 16px；375px 与桌面宽度无溢出。
- [ ] 思考默认折叠，展开收起不影响正文；只有真实摘要/处理信息，不暴露工具参数。
- [ ] 生成成功自动出现起始建议；点击一次只发一条带当前行程范围的消息。
- [ ] 不同目的地、日期、饮食要求得到对应上下文；查询行为不触发修改或重新生成。
- [ ] 美食卡片可追溯至真实候选，信息不足诚实降级；无明确地点的内容不可直接添加。
- [ ] 添加后目标日期出现餐饮活动、地图和受影响交通同步，新版本和对话保持关联。
- [ ] 推荐位置明确时一次点击即可添加，无二次确认；调整位置后按用户实际选择添加。
- [ ] 无合理默认位置时要求选择位置；已有同餐次安排不被静默覆盖，连续添加不制造重叠用餐。
- [ ] 添加成功后其余卡片重新校验；已添加状态从实际行程恢复，删除活动后不残留错误状态。
- [ ] 重复点击/断线后重试只产生一次活动和一次新版本；失败不会出现“已添加”。
- [ ] 旧版本、未保存草稿、跨账号行程、过期候选、冲突时段均有明确处理，不修改错误目标。
- [ ] 停止/中断保留部分回答并能恢复；刷新后完整消息、卡片及已添加状态一致。
- [ ] 上翻历史时不强制滚底；输入法回车、换行、键盘折叠、停止按钮均可用。
- [ ] 桌面与窄屏右上角可见“历史版本”；列表倒序、版本时间及当前/最新标记正确，仅一版、加载失败和空态可区分。
- [ ] 历史查看可浏览当版列表与地图；刷新后仍只读，编辑、自动保存、路线写回及对话修改均不会改动历史。
- [ ] 当前 v5 恢复 v2 产生内容一致的 v6，v1～v5 原样保留；恢复后可继续聊天和添加美食，操作锚定 v6。
- [ ] 恢复前草稿先保存；失败不离开、不丢草稿；跨用户、跨版本链、并发冲突和重复请求均正确处理。
- [ ] 恢复不回滚聊天历史或消耗 AI 额度；无会话行程也可恢复；历史源和旧最新版本不被迟到的自动保存覆盖。
- [ ] 实现后通过 typecheck、web build、相关聊天/版本链/流式测试，并交付浏览器结果供用户验收。
