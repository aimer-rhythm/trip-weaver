# 行程生成主流程审查修复与验收

## 目标与授权

用户要求将上一轮审查的九项问题全部处理，直到验收完成。沿用现有调研、确定性排程、地理增强和标题文案架构；修复实现由代码与既有约束推导，无待确认产品问题。

## 要求与验收

- [x] 初始化、模型、持久化及审计失败均发布唯一终态并释放用户运行锁；超时和取消可收口。
- [x] 行程与成功生成记录在同一 PostgreSQL 事务中提交；失败回滚，不留下无成功记账的行程；取消在事务提交边界处理。
- [x] 所有节奏与美食偏好组合满足每日最多 8 活动，餐次预留容量。
- [x] 候选不足、闭馆等产生的自由安排日也满足美食完整性约束。
- [x] 景点先后硬约束贯穿链起点和段内排序，保持缺端点/无坐标降级兼容。
- [x] 日期分配在存在完整无闭馆解时不丢景点；不可满足时仍如实降级并记录冲突。
- [x] 缺失评分/提及保持未知，合并与排序使用中性兜底，真实零仍为零。
- [x] SSE 增量重连保留历史并按事件 ID 去重，任务切换重置接收位置。
- [x] SSE 终态重放无未初始化异常，释放心跳和订阅，重复断开安全。
- [x] 对应单测/集成/浏览器回归通过；全仓 typecheck、服务端单测、web build、隔离数据库生成 E2E 通过。
- [x] 更新已过时的主流程与恢复规范，记录逐项验收证据。
- [x] 验收发现的取消返回卡住、已完成快照被入口守卫截走问题一并修复并覆盖浏览器回归。

## 技术方案

复用现有边界：编排器统一异常和终态；tripService 允许事务客户端，生成事务在服务边界协调；排程采用受约束最近邻和有限天数精确日期匹配；SSE 分离缓冲重放与实时订阅的资源生命周期。

考虑的相邻场景包括失败审计二次失败、初始化期间取消、事务回滚、修订来源、缺坐标与循环约束、无法全部避让的日期、重复终态和重复事件。保持单进程内存任务模型；不引入队列、额外依赖或数据库迁移。

上一轮在当前 master 上以最小排程样例、依赖故障注入和实际 hook 源码模拟确认问题；现有服务端单测和 typecheck 原本均通过。工作区已有 `.claude/settings.local.json`，不属于本任务。
