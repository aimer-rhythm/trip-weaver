# 行程专属建议

## 1. 范围
生成第三阶段、最终路线、知识库材料、行程 JSON 保存与总览展示。标题依旧并发撰写；建议必须等待远郊修复、跨天分组和最终排序结束。

## 2. 签名
- `prepareTripAdviceEvidence(trip, retrieve, signal)`：按最终活动名称每批最多8个检索，城市隔离、SQL-only；仅保留名称、明确别名/成员匹配。
- `runTripAdviceWriter(trip, evidence, options)`：复用 runner、模型配置、取消信号、审计与用量统计。最多3轮，成功工具提交才算完成。
- `submit_trip_advice({suggestions,cautions})`：模型仅提交标题、正文、activityIds、evidenceIds；来源链接由服务端按证据回填。
- `tripAdviceInputSnapshot(trip)` / `personalAdviceIsCurrent(trip)`：共享的建议有效性判断。

## 3. 契约
- `Trip.meta.advice? = {version:1,generatedAt,inputSnapshot,suggestions,cautions}`；可选字段兼容旧行程，随现有 JSON 存储与导入导出，无新增数据库列。
- 新生成每栏1–2条，标题1–12字、正文1–60字，一句话表达重点；旧快照继续接受原来的1–4条、40字标题和240字正文，避免破坏历史导入/保存。
- 界面完整展示全部条目和正文，不截断、不折叠，无展开/收起按钮；强天气风险置顶。每条关联1–12个活动，最多6条来源。
- 材料保留预约状态、分项政策、证据强弱及原始来源；社区 direct 不等于官方认证，weak/risk_only 不得升级为确定事实。具体政策必须有依据并提示核实。
- 第三阶段标题请求用 review/round=1，建议请求用 review/round=2；review 的 phase_end 在建议返回之后。两次请求累计进入生成用量。
- 标题工具不可重写活动说明。建议工具不可修改行程结构，不接收任意来源 URL。
- 总览以当前专属建议为主体，实时天气与系统 reviewNotes 另行追加。没有专属内容时用原有规则兜底。
- 日期、活动顺序/内容、出行方式、偏好、预算、住宿等变化使建议过期；标题、封面、天气、版本ID和保存时间不影响有效性。
- 过期建议保留在快照里，但不作为当前建议展示；页面显示待更新与基础提醒。重新规划会撰写新内容；手动编辑不会自动调用模型。

## 4. 校验与错误
| 情况 | 行为 |
| --- | --- |
| 活动ID不存在、证据ID不存在或不属于本条活动 | 原子拒绝，允许模型修正 |
| 空白标题/正文、两栏重复正文 | 原子拒绝 |
| 数量/长度/结构非法 | runner 工具 schema 拒绝 |
| 知识库失败 | 空材料，仍可从实际行程推导建议 |
| 模型失败或未提交 | 不保存半成品，基础提醒兜底，行程仍成功 |
| 用户取消 | 中止后续检索/模型/落库，不能降级成成功 |
| 天气变化 | 重新计算天气提醒，不使专属建议过期 |

输入材料只作为不可信数据，提示词拒绝其中的任务指令。来源ID校验保证引用存在与地点关联，不证明模型每句推断的事实准确性；真实文案质量仍需用户验收。

## 5. 示例
- Good：最终第2天游览故宫，模型读取对应弱证据，以“有游客反馈”表达体验并引用已有链接。
- Base：旧行程无 advice，继续显示天气、交通及预约提醒。
- Bad：模型读取并行修复之前的第1天安排，保存“第1天故宫”到最终行程；或把城楼政策泛化到整个广场。

- `apps/web/tests/trip-weather-browser.mjs`：桌面/手机专属建议、来源链接、待更新、旧天气状态和零浏览写入。

## 7. 错误与正确做法
错误：在标题并行请求里读取草稿并写“第几天”建议，然后继续换天修复。
正确：标题并发；待最终结构稳定后单独调用建议工具，保存同一输入快照。

错误：每次保存/天气刷新比较 `updatedAt` 并重新调用模型。
正确：比较建议相关的语义输入；手动变化只标记待更新。
